# Chess Club (local-only)

Next.js 16 app, Bun for packages, Tailwind v4. The user deploys it to Vercel from their own GitHub repo; Claude never pushes, commits to a remote, or deploys.

- Data: behind the async storage layer in `src/lib/db.ts` (`readDb` is request-cached, `mutate` serializes writes and retries on version conflicts, `replaceDb(next | (current) => next, label)` for import/restore/reset, sharing the same write queue as `mutate` and `takeSnapshot`; `wasPersisted(db)` tells whether a state object was the one saved, so side effects of a lost retry are dropped, `listBackups`/`readBackup`). Without `DATABASE_URL` it is the JSON file `data/db.json` (override folder with `CHESS_DATA_DIR`) with daily snapshots in `data/backups/` (pre-change state in both backends; `pruneBackups` keeps 30 daily and 30 deliberate ones, counted apart); with `DATABASE_URL` (Neon Postgres on Vercel) it is one jsonb row in `club_state` plus `club_snapshots`, tables created on first use. `migrate()` upgrades old data on every read. Pages and actions must `await` every read and mutation.
- Ratings are derived: `recomputeRatings()` in `src/lib/elo.ts` replays all completed, non-forfeit games. Never update ratings by hand.
- Pairing logic: `src/lib/pairing.ts` (random: shuffled greedy tries; Swiss: a pruned depth-first search for the fewest hard+soft rematches, then the smallest score gaps; color balancing incl. no-3-in-a-row, Berger round robin, bracket seeding).
- Knockout state lives in `tournament.knockout.matches`; `src/lib/knockout.ts` (`generateKnockoutRound`, `syncKnockout`, `addMatchGame`) keeps matches, tiebreak games and winners consistent (a withdrawn side hands a still-open match to the opponent and its unplayed games go, so the round can complete; `toggleWithdraw` calls it too), called from actions inside `mutate()` after every result change; tested in `knockout.test.ts`. New game objects come from `makeGame()` in `src/lib/games.ts`.
- Read models: `src/lib/queries.ts` (standings + tiebreaks, crosstable, h2h, streaks, club stats, sessions, knockout placement).
- Mutations: server actions in `src/lib/actions.ts`; destructive ones call `requireAdmin()` (`src/lib/auth.ts`). Results and colour swaps are guarded by `mayEditGame()`: the admin may touch any game, a claimed device (`cc_me`) only boards it plays on; the UIs show read-only chips otherwise. Members create friendly games only through challenges; `recordFriendlyGame` (`RecordPastGame` card on Admin → Data, backdating allowed) is `requireAdmin()` bookkeeping for games played without a challenge or forgotten at the time. The Players page hosts the `ChallengeForm` ("Challenge someone") where that friendly form used to be. Correcting a recorded friendly (no tournament, no session; challenge results included) is admin-only and never clears the result (`setGameResult`, errors `friendlyAdminOnly`/`friendlyNeedsResult`); the admin gets `ResultButtons allowClear={false}` inline on the Games page and behind "Correct result" on a played `ChallengeCard`. `deleteGame` puts a challenge whose game it removes back to `accepted`. Every exported action is wrapped in `run()` (form actions) or `attempt()` (called from client components); both refuse while a member code is set and the device has no club access (`isMember()`), except the ways in (`joinClub`, `login`, `logout`, `setupAdmin`, `resetAdminPassword`, `setLanguage`), which pass `OPEN_GATE`. Every `?next=`/Referer redirect goes through `localPath()` (`src/lib/safe-path.ts`). Form text is capped by `str()` (1000 chars) and names by `nameField()` (80). Throw `UserError` (`src/lib/errors.ts`) for anything the user should read: `run()` redirects back with `?flash=` which `Flash` shows as a toast; `attempt()` returns `{ error }`. Plain `Error` means a bug and hits `error.tsx`.
- Access: `src/lib/tokens.ts` signs stateless cookies for two roles (admin password → `cc_admin`, bound to the password hash via `isAdminToken()` so a new password signs every admin device out; club-wide member code → `cc_member`, bound to the code's hash so a new code signs everyone out). `rotateSessionSecret()` in auth.ts (action `signOutEverywhere`) invalidates every cookie at once. `ADMIN_RESET_TOKEN` env enables the forgotten-password form on `/admin?recover=1` (`resetAdminPassword`, admin or owner). A second, optional **owner password** (`settings.ownerPasswordHash`, `setOwnerPassword`) gates the destructive admin tools: `requireOwner(fdOrString)` in actions.ts is used by `resetData`, `importDatabase`, `restoreBackup`, `removeBackup`, `mergePlayers`, `setMemberCode`/`clearMemberCode`, `changePassword`, `signOutEverywhere`; while none is set, admin suffices. `ConfirmButton` takes `password=<placeholder>` to collect it and passes it as the action's last argument; forms send it as the `owner` field. `log()` appends `[owner]` when the actor passed that check. Only the current owner password (or the recovery token) can change it, never the admin password. `src/proxy.ts` redirects to `/join` when `settings.memberCodeHash` is set and no valid cookie is present; `/join`, `/admin` and `/api/*` are exempt. No code set = open club (local default). A third cookie `cc_me` (role "self", `playerId`, bound to the player's PIN hash so a new or reset PIN signs the player's other devices out; pass the hash just written to `setMeCookie(id, pinHash)`) is the device identity, issued by `claimWithPin` only after the player's 4-digit PIN (`Player.pinHash`, scrypt) is set or verified; brute-force brakes for PIN, admin, owner password and member code share `src/lib/lockout.ts` (a try is claimed with `reserveAttempt` inside mutate before the secret is checked, then `failAttempt`; 5 fails lock for 10 min, doubling with every further lock up to ~21 h until a right answer; PIN counters on the player via `src/lib/pin.ts`, `settings.adminLock` / `memberLock` / `ownerLock` through `reserveTry`/`failTry`/`clearTries` in actions.ts); cookies get `Secure` over HTTPS (`secureCookies()`), `ADMIN_RESET_TOKEN` must have 32+ characters; `currentPlayerId()` in auth.ts reads it. Organising actions (`createTournament`, `generateNextRound`, `setParticipants`, `setTournamentStatus`, `toggleWithdraw`, `updateRoundPairings`, all `session*` except delete) call `requireMember()` (admin or claimed device); pages compute `member = admin || !!me` (or `isMemberDevice()` in auth.ts) and swap their controls for `GuestNotice` (`src/components/GuestNotice.tsx`) for guests. Self-only actions (`setAvatar`, `changeOwnPin`) accept the claimed player or the admin; `resetPin`, `updatePlayer`, `deletePlayer`, `addPlayer` are admin-only; `registerSelf` lets an unclaimed device add exactly one player (itself) with a PIN. `/me` is the welcome/picker/PIN screen; `proxy.ts` sends devices without `cc_me`, `cc_skip` or `cc_admin` there once (skip cookie lasts 30 days).
- Challenges: `db.challenges` (`Challenge` in types.ts: from/to, `at`, place, time control, note, status pending/accepted/declined/played/cancelled/expired, `proposedBy`, `rated` (agreed when sent via the `rated` radio, default on; `migrate()` sets `true` on older records; copied onto the game by `recordChallengeResult`, no checkbox at the board; the card header carries an "Elo" / "unrated" pill next to the status pill), `gameId`). Pure helpers in `src/lib/challenges.ts` (`effectiveStatus` treats open ones a day past `at` as expired, `recordable(c)` keeps an agreed one (it has `whiteId`) recordable after that, and `ChallengeCard` still shows its result form, `openBetween` lists every open challenge of a pair (several games on different dates are allowed; `challengeCheck` refuses only the same minute twice, `exists`, and more than `MAX_OPEN_PER_PAIR` = 5 open, `tooMany`; the profile page lists them all), `expireChallenges` writes that inside mutate, `pendingFor`/`sentBy`/`upcoming`/`history`, `challengeCheck`, `combineDateTime`, `toIcs`, `googleCalendarUrl`, `estimateDurationMinutes` for the calendar slot: 2 × (base + 40 × increment) rounded to quarter hours, 30-minute floor and default); actions `createChallenge` (place and time control are required, server-side too: `challengeDetails`; a session has no time control, the form hides the field and the action stores `""`; the "Right now" button is the client component `NowButton`, which only fills date+time with the device's current minute, and `challengeCheck` tolerates `PAST_GRACE_MS` = 15 min in the past so that minute still passes), `answerChallenge`, `proposeChallengeTime`, `cancelChallenge`, `recordChallengeResult` (creates the friendly game via `makeGame`) are member-only via `challengeActor()`, the admin may act for anyone. Colours are drawn at acceptance (`drawColors`, stored in `whiteId`; a new time proposal clears them). A challenge can also be a **session** (`Challenge.session = { minutes, scoring }`, form fields `kind`/`minutes`/`scoring` parsed by `parseSession`, lengths `SESSION_MINUTES` 30–180, labels `challenges.durations`): `scoring: "single"` is recorded like a normal challenge (one game for the whole session); `scoring: "each"` collects games in `Challenge.gameIds` via `addSessionGame` (colours from `nextSessionColors`: the draw first, then alternating; each game a friendly timed inside the booked block) and closes with `finishSession` (needs one game, notifies the score from `sessionScore`); `recordChallengeResult` refuses such sessions, cancel and new-time proposals refuse once games exist, `deleteGame` drops a game from `gameIds` and reopens a finished session left empty; `challengeGameIds(c)` reads either shape; the calendar slot uses the session length. UI: `/challenges` page, `ChallengeCard` (server) in `src/components/ChallengeCard.tsx`, `ChallengeForm` (client, `src/components/ChallengeForm.tsx`) driven by `useActionState(createChallenge)`: the action returns `ChallengeFormState` (`{ error, values }` on a `UserError` so the form keeps what was typed, `{ ok }` on success so it remounts empty; toasts via `useToast`), gets only `challengeOpponents(db)` (id/name/rating/avatar seed, never the player record) plus `today` from the server, picks the opponent with `OpponentPicker`, a thin wrapper over `PlayerPicker` (`src/components/PlayerPicker.tsx`: results are an absolute dropdown shown only while the box is focused or has text, type-to-filter, A–Z or Elo sort, Enter takes the top match, items select on `onMouseDown` so blur does not close the list first; chosen player becomes a chip with a hidden field named by `name`; the search box is `required` until someone is chosen; controlled via `value`/`onChange` + `exclude` when two pickers must know about each other, as in the Admin merge tool's `MergePlayersFields`; `showGames` adds the game count; picker strings live in `common.pick*`). Player data for pickers comes from `src/lib/pick.ts` (`PickablePlayer`, `pickable`, `pickableWithGames`), never the raw `Player` (PIN hash). and takes the time control from `TimeControlField` (`src/components/TimeControlField.tsx`: preset chips `TIME_CONTROL_PRESETS` 1+0 / 3+2 / 10+0 / 10+2 plus a free field filtered by `cleanTimeControl`; `TIME_CONTROL_RE` = minutes with optional +increment, checked server-side too: `timeControlFormat`), home card, profile card, header badge (`waiting` prop on `Nav`), `/api/challenge/[id]` serves the `.ics` to the two players.
- Time: the server runs in UTC on Vercel, the club in Berlin. Never use `new Date().toISOString().slice(0, 10)`, `getHours()`, `toLocaleString` without a zone or `new Date("YYYY-MM-DDTHH:MM")` for club-facing values. `src/lib/time.ts`: `clubTimeZone()` (`CLUB_TIME_ZONE` env, default Europe/Berlin), `localDay()`/`localTime()`/`localMonth()` (instant → club wall clock), `dayOf(value)` (plain date stays, ISO instant converts), `sameLocalDay`, `zonedToUtc(date, time)` (form fields → ISO instant, DST-aware), `daysFromToday`, `localStamp(iso)` ("YYYY-MM-DD HH:MM" for activity-log lines, which the phone notifications repeat verbatim). `formatDate/formatDateTime` pass the zone; `combineDateTime`/`isToday` in challenges.ts delegate; `playedAt`, month keys, season bounds and every "today" default use it. The `/games` month filter compares `localMonth(completedAt)`; it shows the last `MONTH_CHIPS` = 3 months with games as buttons and older ones in the client `MonthSelect` dropdown, and hides itself while all games fall in one month. Tested in `time.test.ts`; `bun test` must pass under any `TZ`.
- Activity log: call `log(db, text)` inside the `mutate()` that persists a change; `db.activity` keeps the last 500 entries, shown on the Admin page (searchable via `?q=&who=&all=1`).
- Admin **Switches** card (top of the Club tab on `/admin`): every on/off in one place. Owner password (off via `clearOwnerPassword(owner)`, needs it once more; on links to the Security form `#owner`), member code (off via `clearMemberCode`; on links to `#member`), and the plain flags `settings.selfSignupOff` / `clubNotifyOff` / `slackOff` flipped by `setSwitch(key, on)` (unset = on). `registerSelf` refuses while sign-up is off (`signupClosed`) and both sign-up forms show that text instead; `log()` skips the admin feed while `clubNotifyOff`; `tellClub` stays quiet while `slackOff` or without `SLACK_WEBHOOK_URL` (the switch then shows the missing variable).
- Slack channel: `src/lib/slack.ts` (`slackWebhook()` reads `SLACK_WEBHOOK_URL`, only `https://hooks.slack.com/services/…` counts; `slackEscape` for mrkdwn; `slackRequest` builds the JSON post; `sendSlack` never throws, no webhook = no network call). `tellClub(db, c, text)` in actions.ts queues a post in the actor store (`Actor.slack`, sent by `notifyPhone()` like the ntfy lines, only if the attempt was persisted) for a new challenge, an agreed one and a result / finished session, in the club language (`challenges.slack.*`); the text comes from the pure `slackLine()` in `src/lib/slack-lines.ts`: names, time, place and format only, never notes. Declined, withdrawn and new-time proposals are not posted. The Admin switch `slack` (`settings.slackOff`) turns it off. Members no longer have their own ntfy topics: `migrate()` drops `Player.notifyTopic` and `settings.memberNotifyOff`; ntfy is the admin's feed only.
- Phone notifications: `src/lib/notify.ts` (`ntfyTopic`/`ntfyServer`/`ntfyLabel` read `NTFY_TOPIC`/`NTFY_URL`, `ntfyRequest` builds the JSON publish, `sendNotifications` POSTs and never throws). `log()` also pushes the line into the actor store (`Actor.notes`); `run()`/`attempt()` call `notifyPhone()` on success, `UserError` and redirect (not on a plain `Error`, whose mutate may not have saved), which dedupes by text (mutate retries rerun the callback) and sends via Next `after()`. No topic = no network call at all. The activity card on Admin shows a "Phone: on/off" badge via `ntfyLabel()`. Tested in `notify.test.ts`.
- Data health: `checkHealth(db, msgs?, raw?)` in `src/lib/health.ts` (read-only consistency report: dangling refs, misplaced games, knockout winners, rating drift) feeds both the Admin "Data health" card and `.claude/skills/inspect-db/inspect.ts`. Security headers (CSP with frame-ancestors/form-action/base-uri, nosniff, referrer, permissions, `X-Robots-Tag: noindex`) live in `next.config.ts`.
- Admin bulk tools: `src/lib/reset.ts` (pure `applyReset(db, scope)` for the Danger zone; action `resetData` snapshots via `replaceDb(next, "before-reset-<scope>")`), `src/lib/merge.ts` (`mergeCheck`/`mergePlayers` rewrite every player reference; refused when the two ever met; the Admin form uses two `PlayerPicker`s via `MergePlayersFields`, the duplicate side in the loss tone), snapshots by hand via `takeSnapshot`/`deleteBackup` in db.ts (`BACKUP_NAME_RE`, `snapshotLabel`), `/api/backup?snapshot=<file>` downloads one. Downloads go through `exportable()` (`src/lib/export.ts`: no session secret, password/code hashes or locks; player PINs stay), and import/restore apply `keepInstallation()` so this installation's passwords, member code and locks survive. Challenges follow players and games: `pruneChallenges()` (challenges.ts) runs after `applyReset` and `deletePlayer`, `mergePlayers` rewrites them. `Qr` (`src/components/Qr.tsx`, `qrcode` package, server-only) + `requestOrigin()` (`src/lib/request-url.ts`) render the phone QR on Admin.
- Club layer: `src/lib/club.ts` (titles by rating band from `TITLE_GAMES` games, derived achievements, seasons + `seasonTable`, tournament winners, month champions, home highlights). `db.seasons` is the only stored state; `migrate()` opens a first season when none exists. Club identity lives in `settings.club` (no motto: the quote of the day replaced it; `migrate()` drops the old field). `seasonOverdue()` flags a season that ran past its year so Admin and the home hero nag to close it.
- Avatars: `Player.avatar` is a seed string; `face(seed)` in `src/lib/avatar.ts` derives a flat cartoon character (skin, hair style and colour, head shape, eyes, mouth, brows, accessory, shirt, ground colour) and `FaceSvg` draws it as SVG. `migrate()` seeds missing ones with the player id, `addPlayer` uses a random seed, the edit form offers `avatarChoices()`. `Avatar` in `ui.tsx` looks the seed up via a per-request `cache()` of `readDb()`, so `ui.tsx` must stay server-only.
- Tables: `.table` cells are `px-3`; columns beyond the essentials hide below `lg`/`xl` (`hidden lg:table-cell`) so no table needs horizontal scroll down to 1024 px; the tournament standings table uses `[&_th]:px-2 [&_td]:px-2`. Alternate build folders must stay in `.gitignore` (`/.next-*/`), otherwise Tailwind scans them and breaks the CSS build.
- Layout: two-column pages use `grid gap-6 lg:grid-cols-[3fr_2fr]` with default stretch; a column that holds several cards is a `div.col-stack` (flex column, last card grows) so both columns end on the same line; `/challenges` is the exception (`lg:items-start`, plain `flex flex-col gap-6` columns): the form column is short next to lists that grow with club life, so stretching would show a void. The home page has no tall side column: `MyChallenges` is a full-width strip under the stats (rows in `md:grid-cols-2`), then Rankings (12 rows) and Recent games (10 rows) side by side with default stretch, then Tournaments / Around the club as one `md:grid-cols-2` row; the club-night link sits full width above the grid. There is no separate "Upcoming games in the club" card: the strip ends with an "Elsewhere in the club" group (other members' agreed games), and for a guest device it is that group alone under the club-wide title, so a game never appears in two cards. On `/challenges` the admin also has a whole-club view (`?view=club&status=&player=`, the only view for an admin device without a claimed player; a Mine / Whole club switch otherwise): `clubChallenges`/`clubGroup`/`CLUB_FILTERS` in challenges.ts, groups waiting / agreed / played / declined-withdrawn-expired, status tabs plus a plain GET player filter, 40 cards per group. The left column holds every list (open, upcoming, sent, club-wide, played) and the declined/withdrawn/expired ones fold into a `<details>` line with a count; the right column is the form alone, wrapped in `Foldable` (`src/components/Foldable.tsx`: open on `lg`, folded behind a tap on phones) and ordered first on phones (`order-first lg:order-none`) so the form sits on top without hiding the lists. The home page shows `MyChallenges` (`src/components/MyChallenges.tsx`: what waits for my answer with inline Accept/Decline, what I sent with Withdraw, my agreed games, then everyone else's agreed games; six rows, then "n more") as the strip described above. The site footer is the club name alone (same locally and on Vercel). Admin-only tools never sit at the bottom of a member page; they live on `/admin`. `Section` is a flex column whose body grows.
- Visual language: display serif `font-display` (Fraunces) for h1/card titles, Geist for body; `KnightMark` logo (a knight split down the middle: left half `currentColor`, right half `--accent`, overridable via `--knight-left`/`--knight-right`, `mono` for one colour; drawn standalone without a tile so it reads as one shape next to other favicons; `public/icons/icon.svg` is the same mark with a `prefers-color-scheme` swap, the PNG app icons put it on the dark `#0e1014` ground and were rendered with `qlmanage -t -s 512`) and `Icon` line icons in `src/components/icons.tsx` (no unicode chess glyphs or emoji for UI chrome); `.board-texture` for the hero; medal `Rank` circles; `QuoteOfTheDay` (`src/lib/quotes.ts`, rotates by calendar day) instead of a motto. Daily puzzle: `src/lib/puzzles.ts` holds 365 Lichess-database puzzles (CC0; picked by rating 850–1700 and popularity, each line checked with chess.js when the list was built; `fen` after the opponent's move, `moves` in UCI, `alt` other mating finishes), `puzzleOfTheDay()` rotates by club day like the quote; `src/lib/board.ts` is the tiny client-safe FEN/UCI player (castling, en passant, promotion, no legality: only the solution counts); `DailyPuzzle` (client, home page, bottom row, a third on `lg`) with SVG pieces from `PieceSvg`, a Hint button (glows the piece to move), Show solution, Start over and an "Open on Lichess" link; solved state per device in localStorage (`puzzle:<day>` = `solved:<misses>[:h]` / `shown`), nothing sent to the server or to Lichess; board colours `--sq-light`/`--sq-dark`; texts in `messages/puzzle.ts`; tested in `puzzles.test.ts`. Do not put `<title>` inside SVGs (hydration mismatch); use `aria-label`.
- Routing: `src/app/(site)/not-found.tsx` / `src/app/not-found.tsx` share `NotFoundCard` (translated 404), `src/app/(site)/loading.tsx` is the spinner while a dynamic page renders; `src/app/layout.tsx` is html/body only (plus PWA metadata; `src/app/manifest.ts` serves the manifest, icons in `public/icons/`); `src/app/(site)/layout.tsx` adds Nav, centered `main` and footer. `src/app/tv/page.tsx` is the projector view outside `(site)`: no nav, big type, `AutoRefresh` every 5 s, exempt from the `/me` identity prompt in `proxy.ts`. Club night and running tournament pages mount `AutoRefresh` (10 s, `router.refresh()`), and highlight the claimed device's own board via `currentPlayerId()`. Admin sign-in is reachable only by typing `/admin`; the header shows the Admin badge only while signed in. The admin cookie lasts `ADMIN_HOURS` = 12 (tokens.ts; `isAdminToken` also refuses tokens that run further out, i.e. the old 30-day ones); signing in keeps the device's claimed player, and while signed in `AdminBanner` (under the header in the `(site)` layout) says so and offers `logout`, which ends admin mode only.
- Languages: English and German only, no hard-coded UI strings. Dictionary in `src/lib/i18n/` (`index.ts` builds `Dict` from `messages/<namespace>.ts`, each exporting `{ en, de }` with `de: typeof en`, so a missing German key fails `tsc`; values are plain strings, `{name}` placeholders via `fmt()`, plurals `{ one, other }` via `plural()`). Server code: `const { t, lang } = await getT()` from `src/lib/lang.ts` (per-request cache; reads the `cc_lang` cookie, else `settings.language`, else en). Client components: `useT()` from `I18nProvider` (mounted in the root layout). `PrefsMenu` (gear in the header) holds both per-device preferences: language (cookie via `setLanguage`) and theme (localStorage, `themeInitScript` in the root layout). Dates: `formatDate/formatDateTime/formatMonth(x, lang)`. Lib code that produces display text (`highlights`, `knockoutRoundName`, `TIEBREAK_PRESETS`, `knockoutPlacement`, error messages) takes a messages object with an English default so tests stay plain. Activity-log texts stay English (stored data). When a file uses `t` for a tournament, destructure `const { t: msg } = await getT()`.
- Pages are server components with `force-dynamic`; interactive bits (`ResultButtons`, `ConfirmButton`, `Toast`, `Flash`, `PrefsMenu`, `SearchBox`, `PairingReveal`) are client components. Round-generating actions redirect with `?reveal=<round>`; `PairingReveal` plays a one-time board draw ("draw" for random pairings, "reveal" for computed ones), strips the query on mount and renders the real boards when done.
